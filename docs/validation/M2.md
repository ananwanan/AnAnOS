working-tree implementation, not a Raspberry Pi run.

Current debug raw images generated with `rust-objcopy`:

| Artifact | Bytes | Behavior |
| --- | ---: | --- |
| `target/kernel8.img` | 163840 | Default MMU-off path |
| `target/kernel8-mmu.img` | 241664 | Opt-in M2 identity-map path |
| `target/bootloader8.img` | 8034 | Existing DTB-preserving UART bootloader |

Both kernels retain entry `0x200000`; bootloader retains `0x80000`. Table pages
come from owned physical RAM, and metadata/stack BSS is excluded from the raw
payload. Kernel text/rodata/writable boundaries are 4 KiB aligned; vectors
retain 2048-byte alignment and the boot stack remains 64 KiB.

The tests cover FDT static/dynamic `no-map`, bad-data/result clearing, mapping
permissions/holes/maximum region counts, high RAM, descriptor encodings,
1 GiB/2 MiB/4 KiB selection, conflicts, offline block splitting/pruning,
allocation exhaustion and physical ownership cleanup. Integration tests run
DTB -> policy -> descriptors with physical allocator tokens, including each
insufficient table budget and 64 fragmented firmware layouts. Existing heap
and physical-page stress checks remain in the same test suite.

Debug disassembly review after `parse_into` shows an approximate largest direct
initialization call chain of 26 KiB including `kernel_main`, within the 64 KiB
stack. This is a static estimate, not measured board stack high-water; indirect
formatting callbacks and recursive sort depth add usage. No large plan or DT
result is returned/copied on the runtime boot stack.

Architecture review checked MAIR/TCR encodings, 40-bit PA bounds, EL1h/CPU0
state, Cortex-A72 MIDR/SMPEN prerequisites, permission descriptors, publication
barriers/TLBI and the pre-/post-enable failure paths. Software walks must precede
M=1; hardware AT probes after activation check data translation rather than XN
instruction-fetch behavior.

## Hardware acceptance is pending

No removable-drive installation, UART upload, or new board UART/HDMI output
was performed in this task. The following remain unverified:

- M1 page/heap checks with real firmware data.
- Firmware SMPEN and MMU activation on Raspberry Pi 4B.
- Hardware AT identity/RO/null checks and register values.
- Heap/page reuse and mailbox roundtrip after MMU enable.
- HDMI scrolling and sustained Generic Timer/GIC IRQ delivery.

After M1 board acceptance, use the explicit `-EnableMmu` upload option and record
actual logs here. Deployment commands and expected diagnostics are documented
in [mmu.md](../mmu.md). M2 is code/build tested, not hardware accepted; caches,
EL0, process address spaces and active page-table mutation remain future work.
